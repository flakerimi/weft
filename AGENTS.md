# AGENTS.md

This file is for agents working on Weft itself. To build with Weft, start from https://weft.base.al/index.md, then https://weft.base.al/llms.txt, or read the skills in `skills/`.

Weft is one UI system for Go and Vue apps. It has Vapor components, a page build, and a Go package that serves the build from one binary. It is pre-alpha, and nothing is published to npm.

## Layout

| Path | What it is |
| --- | --- |
| `version.go` | The root Go package (`github.com/flakerimi/weft`): only `Version`, which a release sets with `-X`. |
| `warp/` | Warp, the Go side of an app (`github.com/flakerimi/weft/warp`): `App` and its modules, `Provide` and `Need`, typed routes with names and permissions, validation, the error shape, cross-site protection, `.env` configuration, `Describe` (what `weft gen` reads), and `Serve` and `WithFiles` for the page build. Standard library only. |
| `warp/data/` | The data layer (`github.com/flakerimi/weft/warp/data`): `data.Module()` opens the database named by `DB_DRIVER` and `DB_URL` through `database/sql` at start and makes the tables; `Store[T]` keeps a model that embeds `data.Record`; `Tx` runs a transaction. SQLite only, behind a small dialect type. It imports no driver: the app does. |
| `warp/auth/` | The login (`github.com/flakerimi/weft/warp/auth`): users kept through `warp/data`, PBKDF2 passwords, a session in a signed cookie, the routes under `/api/auth`, `auth.Can` and `auth.Per` to guard routes, and the owner's one-time setup link; `authtest` signs a test in as the owner. |
| `warp/warptest/` | The test kit for apps and modules built on Warp: an app started from a map of settings, and a client that keeps cookies and decodes answers and the error shape. |
| `dbtest/` | A Go module of its own (`github.com/flakerimi/weft/dbtest`) holding every test that needs a real database, so the SQLite driver `modernc.org/sqlite` is its dependency and never `warp`'s. |
| `cmd/weft/` | The `weft` command: `create`, `dev`, `build`, `gen` (the typed client from the app's description), `routes`, `unpack`, `upgrade`, `catalog`, `version`, `update`. A release stages the bundle (the packages, the catalogue and the template) into `cmd/weft/bundle/` for `go:embed`; in git that folder holds only `README.md`, and a development build reads a bundle from the folder `$WEFT_BUNDLE` names, which also holds the Go package. An app a release makes requires `github.com/flakerimi/weft` at the release's tag, from GitHub; one a development build (`0.0.0-dev`) makes replaces it with `./.weft/go`. |
| `packages/themes/` | Tokens and the `neutral`, `lisa` and `weft` themes. `dist/` is generated. |
| `packages/ui/` | `@weft/ui`. Components are in `src/<group>/<Name>.vue` with `<Name>.docs.md`, the accessibility composables in `src/headless/`, examples in `examples/<Name>/`, tests in `test/`. |
| `packages/vite/` | `@weft/vite`: the page build (`bin/weft-build-pages.mjs`, `src/build.ts`), the page dev server (`bin/weft-dev.mjs`, `src/dev.ts`), auto-imported components (`src/auto-import.ts`), server rendering, Markdown content, islands. |
| `examples/shop/` | The example app, a Go module of its own shaped as `weft create` shapes an app, with the SQLite driver: `data`, `auth` and a `products` resource, a table, a dialog and a run-time page. `scripts/shop.sh` runs it; `cmd/weft/shop_test.go` builds and drives a copy. |
| `templates/app/` | The app `weft create` writes: `main.go` makes a `warp.App`, `app/modules.go` lists its modules, and `app/hello/` is the first. A file ending `.tmpl` is rendered with the delimiters `[[` and `]]` and loses the suffix. |
| `catalog/components.json` | The component catalogue, generated by `scripts/catalog.ts` (`pnpm catalog`). Never edit it by hand. |
| `site-src/` | weft.base.al. It has its pages, the docs in `content/docs/`, the gallery in `gallery/`, the files for agents in `agents/` (`/index.md`, `/llms.txt`, `/llms-full.txt`), the server in `main.go`, and Go tests over the build. |
| `skills/` | Claude Code skills for people building with Weft, served at `/skills/<name>`. |
| `playground/` | A Go binary embedding a Vite app that uses the components. |
| `bench/` | The benchmark against Astro, Nuxt, Next.js and SvelteKit. |
| `scripts/` | Builds and releases: `site.sh`, `playground.sh`, `bundle.sh` (stages the bundle `weft` carries), `release.sh` (stages it into `cmd/weft/bundle/` and builds the binaries, for the systems `WEFT_TARGETS` names), `publish-site.sh`, `github-release.sh` (the GitHub Release of a published version, which `publish-site.sh` runs), `rollback-site.sh`, `shop.sh` (runs `examples/shop` with this repository's Weft: `dev`, `build` or `test`), `catalog.ts`, `sizes.ts`. |
| `docs/superpowers/specs/` | The designs, `2026-11-20-weft-design.md` and, for the Go side, `2026-11-23-warp-design.md`, with their phases, and `2026-11-25-warp-slice-design.md`, the first pass through W2 to W4. |
| `docs/superpowers/plans/` | The plans, one per stage, each with Global Constraints and a Review Focus. |
| `docs/parity.md`, `docs/sizes.md`, `docs/design/` | The comparison with Nuxt UI, each component's size, and the approved designs. |

## Build and test

You need Go 1.26, Node 22.18 or later and pnpm 10. Run everything from the repository root.

```sh
pnpm install
pnpm --filter @weft/ui test           # while working on components
pnpm test                             # every package; builds @weft/themes and @weft/ui first
pnpm typecheck
scripts/playground.sh build           # go test needs all three builds
scripts/site.sh build
pnpm --filter weft-bench build
go vet ./...
go test ./...
(cd dbtest && go test ./...)
```

- `scripts/site.sh` and `scripts/playground.sh` without `build` also run the server, on `:8080`.
- After you change a component's props, its `.docs.md` or an example, run `pnpm catalog`. A stale catalogue fails `pnpm test` (`packages/ui/test/catalog.test.ts` rebuilds it and compares). The site build checks only the examples: it fails when an example file is unlisted, changed or gone, not when props or docs changed.
- `node scripts/sizes.ts` rewrites `docs/sizes.md`.
- `go test ./cmd/weft` stages a bundle, makes apps and installs them from the npm registry, runs `weft dev`, and builds a release with `scripts/release.sh`, which takes minutes. `go test -short ./cmd/weft` skips all of that; `scripts/release.sh` runs the `-short` tests, since the full ones run it.
- `.github/workflows/release.yml` runs on a pushed tag `v*`, and by hand (`workflow_dispatch`, with a `version` that must pass `scripts/version.sh` and `draft_release`, off by default, so a hand run only builds and tests). It runs `go vet` and the full Go tests of the root package, `warp` and `cmd/weft` on Linux, macOS and Windows, the only place macOS and Windows run (`ci.yml` is Linux, on every push). Then it builds all six targets, darwin, linux and windows on amd64 and arm64, with `WEFT_TARGETS="…" scripts/release.sh` (a windows target is a `.zip` holding `weft.exe`), keeps them as the run's artifact `weft-<version>` and, only by hand with `draft_release`, as a **draft** GitHub Release `v<version>`, made by the job `draft`, the only one that may write, which runs no code of the repository's or its dependencies'; it fails if a release of that name exists, and never replaces, deletes or publishes one. On a tag it makes no release. It never publishes the site: weft.base.al stays the release channel, which the installer and `weft update` download from, published by the owner with `scripts/publish-site.sh`, which builds the four darwin and linux targets. Windows is built and tested there, not released.
- A publish tags and releases. `scripts/publish-site.sh <version>` needs the tracked files as HEAD has them (`site/releases.txt` aside); it makes the annotated tag `v<version>` on HEAD and pushes it to `origin` before the site push, so apps can fetch the module at it, and after the push `scripts/github-release.sh` makes the public GitHub Release `v<version>` with exactly the archives and `SHA256SUMS` the site serves. A tag of that name on HEAD already (a publish that stopped after pushing it) is used; on another commit, or a GitHub Release of that name, stops the publish before anything is built. Untracked files (not ignored ones) in what a release or the site is built from stop it too (the script lists those paths). A tag origin has and the checkout does not is fetched, not made again. Without `gh`, or with `gh` not signed in to github.com, the site is still published and tagged, and the publish says what to do (install gh, or `gh auth login`), then `scripts/github-release.sh <version>`, and exits 1. `--dry-run` checks the tag and the release and prints the `git` and `gh` commands. A tag the module proxy has served never moves: a version is never tagged twice.

## How work is done

1. **Plan.** Work follows a plan in `docs/superpowers/plans/`, and the plan follows the spec. Its Global Constraints bind every task.
2. **Test first.** Write the failing test, run it, and see it fail for the reason you expect. Then implement, and see it pass. Check that the key tests catch a deliberate mistake.
3. **Run the full suite** (above) before each commit.
4. **Commit** with a message like `Area: what changed`, then a short list of the changes. Put no `Co-Authored-By` line in it.
5. **Review.** A reviewer who did not write the commit reviews it against the plan's constraints and Review Focus. Findings are fixed in a follow-up, with the tests that cover them run again.

Briefs and reports for a plan's tasks live in `.superpowers/sdd/<plan>/`, which git ignores.

## Rules

- **Vapor only.** Every component is `<script setup vapor lang="ts">`. Never use the Options API, `getCurrentInstance`, `app.config.globalProperties`, `v-memo` or VNode render functions, and never install `vaporInteropPlugin`.
- **Pinned versions.** `vue` is pinned to exactly `3.6.0-rc.16`. Before adding any dependency, run `npm view <pkg> version` and use the latest.
- **Go uses the standard library only.** Nothing is compressed, rendered or hashed per request: it all comes from the build's manifest. The one exception is the nested modules `dbtest/` and `examples/shop/`, which may require a database driver; `warp/` never imports one, not even in a test.
- **Styles use only `--weft-*` tokens**, each with a fallback. New tokens go in `@weft/themes`.
- **Components adapt from inside**, through `useWeft()` and `useWidth()`. Never write a `Mobile*` variant, and never check device names.
- **Error messages** are one sentence that names the file and says what to do.
- **No npm publishing.** Every package is `private`.
- **Never delete with `rm`.** Use `trash`, which can be undone. Never delete the owner's files, and ask before deleting anything. Tests may remove only their own temporary folders.
- **Git.** Never use a bare `git stash`. Commit or push only when asked.
- **Publishing is the owner's step.** Never run `scripts/publish-site.sh`, `scripts/rollback-site.sh` or `lisa` without `--dry-run`. Releases in `site/releases/` are git-ignored; copy them, never move them.
- **Never edit generated files**: `catalog/components.json`, `packages/themes/dist/`, any `dist/`.
- **Docs describe the code as it is.** Something not built yet goes in `site-src/content/docs/coming-next.md`, with its phase.
